# スマホで崩れないことを確かめる

**開発に使う OS を限定せず、利用可能な環境で確認を進める。** Windows・macOS・Linux のいずれでも、まずブラウザの端末エミュレーションで幅・タッチ向けの配置・横のはみ出しを確かめる。対象端末の実機やエミュレーターがあれば、続けて端末固有の挙動を確かめる。

PCのブラウザを狭めた検証は、iPhone の代わりにならない。セーフエリア、Dynamic Island、ホーム画面から起動したときの挙動、キャッシュの残り方は、どれも Chrome の狭い窓では再現しない。iOS 固有の挙動は iPhone 実機か macOS の iOS Simulator で確かめる。Android は実機か利用可能な Android エミュレーターで確かめる。**対象端末で試していない項目は未確認として残し、ブラウザの確認結果と区別する。**

利用者は「スマホで見てみて」としか言わない。利用可能なブラウザや端末での表示から撮影までは自分で進め、結果は撮った画面と「どこが崩れていて、どう直したか」で伝える。iOS Simulator は macOS と Xcode がある場合だけ使う。使えない環境でも共通の確認を進め、実機が必要な項目と、同じネットワークの実機から開く URL を伝える。

## 1. 見る順番

- **画面の全種類を開く。** トップ、子画面、ダイアログ、ログイン画面のそれぞれ
- **直す前にも一度見る。** 症状を自分の目で確かめてから原因を探す
- **指摘された所だけを見ない。** 1回に1つしか指摘されなくても、同じ画面に写っている他の崩れも直す。最低限この順で見る
  1. **上端**：ステータスバーの帯と本文の色がつながっているか。画面ごとに色が違っていないか
  2. **浮いている要素**：固定のボタンやバッジが、見出しや本文に重なっていないか
  3. **余白**：最初の見出しまでの空きが間延びしていないか。余白を足し算で積むと、元から余裕のある画面だけ広くなる。`max()` で下限を保証する形にする
  4. **下端**：中身の短い画面で、下に出る地の色。上下に引っ張ったときに見えるのは `html` の背景色
  5. **横**：`document.documentElement.scrollWidth === clientWidth`
- **数字のカードは、文字の矩形がカードに収まっているかを測る。** 画面からはみ出していなくても、隣のカードへはみ出すことがある。実際の桁数と、列数が変わる境目の幅で測る。文字を縮めて収めず、同じ種類の数字の大きさはそろえたまま、桁の丸め方やカードの幅を見直す

## 2. 確認環境の選び方

### 全 OS 共通

- **まず使用中の OS と利用可能なツールを確かめる。** macOS の `xcrun`・`open` を Windows や Linux で実行しない
- **ブラウザの開発者ツールか利用可能なブラウザ自動操作で端末表示にする。** 対象の縦向き・横向きと列数が変わる境目を開き、画面幅・高さ・タッチ設定を記録する。狭い表示だけでソフトウェアキーボードや実機の Safari を確認済みにしない
- **開発サーバーはプロジェクト既存の起動方法を使う。** 実機から開く場合は、サーバーを LAN から到達できるアドレスで待ち受けさせ、PC の LAN アドレスとポートを使う。実機の `127.0.0.1` は実機自身なので使わない。必要なネットワーク設定と、確認後のサーバー停止も案内する
- **スクリーンショットは作業用フォルダへ保存する。** 共通手順で `/tmp` など OS 固有の一時パスを決め打ちしない。自動処理で一時フォルダが必要なら `os.tmpdir()` と `path.join()` を使う
- **実機固有の項目は対象環境で確かめる。** セーフエリア、ホーム画面起動、ソフトウェアキーボード、アプリ内ブラウザを、確認できたものと未確認のものに分けて報告する

### iOS Simulator（macOS と Xcode がある場合）

以下は macOS のシェル専用。`<UDID>`・`<port>`・`<path>`・`<一意の値>` を実際の値に置き換え、画像はカレントディレクトリへ保存する。

```bash
xcrun simctl list devices booted                 # 起動中があれば、それを使う
xcrun simctl list devices available
xcrun simctl boot <UDID>
open -a Simulator
xcrun simctl openurl <UDID> "http://127.0.0.1:<port>/<path>?cb=<一意の値>"
xcrun simctl io <UDID> screenshot sim.png
xcrun simctl shutdown <UDID>                     # 自分で起動した端末だけ終了する
```

- **`xcode-select` がコマンドラインツールを指していて `simctl` が見つからないときは、`DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer` を渡す。** `xcode-select` を切り替えなくても動く
- **Mac 上の開発サーバーは、Simulator から `127.0.0.1` でそのまま開ける。** 認証の要る本番を開かなくても、ビルド結果を検証できる
- **開き直すときは URL に乱数のクエリを付ける。** 付けないと前の版が出る
- **`openurl` の後は10秒ほど待ってから撮る。** 早いと真っ白な画面か、読み込み途中が写る。白い画像が撮れたら、まず待ち時間を延ばして撮り直す
- **端末は1台を使い回し、自分で起動した端末は終わったら畳む。** 何台も起動したまま放置すると、メモリを食い合って中のプロセスが落ちる。元から起動していた利用者の端末は終了しない
- **Mac の画面全体を操作するツールで Simulator をタップしない。** 利用者の作業からフォーカスを奪う。`simctl` にタップは無いので、次のように別の方法で同じ結論を出す
  - 引っ張ったときの地の色は、`html` と `body` の `background-color` を読んで同じ色かを確かめる
  - ホーム画面から起動したときの見え方は、セーフエリアを CSS 変数へ通しておき、値を差し込んで再現する
  - ホーム画面への追加のように、画面操作でしか届かない状態は、人に一度だけ確認を頼む

## 3. セーフエリアと上端

```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
<meta name="theme-color" content="#1f3a8a">
```

- **背景は画面の端まで広げ、文字とボタンだけを安全な領域へ逃がす。** `viewport-fit=cover` だけでは中身も Dynamic Island の下に入る。逆に帯ごと押し下げると、背景が手前で切れる

```css
.hero { padding-top: calc(3rem + env(safe-area-inset-top, 0px)); }
.hero-inner {
  padding-left: max(1rem, env(safe-area-inset-left, 0px));
  padding-right: max(1rem, env(safe-area-inset-right, 0px));
}
main { padding-bottom: calc(4rem + env(safe-area-inset-bottom, 0px)); }
```

- **ホーム画面から起動する Web アプリは、Safari のタブとは別物として確かめる。** 判定は `display-mode: standalone` に加えて `navigator.standalone === true` も見る。最初の画面だけでなく、遷移する先の全 HTML に同じ meta を付け、値をそろえる。食い違うと、どちらが使われるかが iOS の実装しだいになり、直したのに直らない状態の切り分けができなくなる
- **`apple-mobile-web-app-status-bar-style` は、上端の色をつなぐか、ぼかしを避けるかの選択になる。** `black-translucent` は中身をステータスバーの裏まで描くが、iOS 26 以降はそこへ OS がぼかしを重ねる。`default` にすると中身はステータスバーの下から始まり、その帯は `theme-color` で塗られる。両方は取れないので、先にどちらを取るか決める。`default` でもぼかしが出る報告もあり、OS の版によって振る舞いが変わる
- **Safari のタブで、上端の帯の色を本文の帯とつなぎたいとき** は、画面の上端に接する高さ 0.5rem ほどの `position: fixed` の面を置き、帯の色で塗る。帯を通り過ぎたら隠す。スクロールに合わせて `theme-color` や `body` の色を差し替えない
- **帯の直後の本文の入れ物は `display: flow-root` にする。** 最初の子要素の上マージンが外へ抜けると、地の色が細い線として見える

## 4. スクロール

- **縦のスクロールは `document.scrollingElement` の1つだけにする。** 画面全体を覆う `overflow-y: auto` の入れ物を作らない。iPhone の「画面の上端をタップして先頭へ戻る」が使えなくなる
- **長い本文を `iframe` の中でスクロールさせない。** スマホでは本文の URL へ直接遷移させる。そのとき、遷移前の画面にあった操作（一覧へ戻る、共有）を消さず、本文の上に小さく重ねる
- **横長の表など、横のスクロールは部分的に持ってよい**
- **横のはみ出しは原因を直す。** `overflow-x: clip` は直した後の保険で、代わりにしない。`touch-action: pan-y` は Safari の戻るジェスチャーに影響するので既定では使わない

## 5. 入力とタッチ

- **入力欄の `font-size` は 16px 以上にする。** iOS Safari は 16px 未満の入力欄にフォーカスすると画面を拡大し、ページが横にはみ出したまま戻らない。小さく見せたいなら `padding` と `height` で詰める。1つ足したら、画面内の全部の入力欄を見る
- **メニューはホバーではなくタップで開く。** 外側のタップで閉じるには `mousedown` に加えて `touchstart` も拾う
- **ボタンで入力欄を開くなら、同じイベントの中で `focus()` を呼ぶ。** タイマーや次の描画へ回すと、キーボードが出ないことがある
- **キーボードの有無の判定と、配置の高さを分けて扱う。** アプリ内ブラウザ（WKWebView）では、キーボードが出ると `innerHeight` と `visualViewport.height` が両方縮むことがある。入力前の高さとの比較も判定に使う。キーボードが閉じる途中も、しばらく表示領域は縮んだままになる
- **送信ボタンは二重送信を検査する。** タッチの終わりで送信する作りなら、ドラッグ、タッチの中断、複数の指を除外し、続いて来るクリックで2回送らないかを確かめる

## 6. アプリ内ブラウザ

- **SNS アプリの中のブラウザは、ページを描いた後で上の余白を足すことがある。** そのとき `resize` も `visualViewport` の通知も来ない。読み込み時に測った見出しの高さで配置した要素が、見出しに重なる。見出しを `ResizeObserver` の `border-box` で見張って配置し直す
- **Safari や検証用の WKWebView で直っても、対象のアプリで直った証拠にはならない。** 再現できていない症状は、原因が分かった、直した、と書かない

## 7. 検証の記録で間違えないこと

- **撮った画像が新しい版のものかを照合する。** 開発サーバーがファイルの変更を拾わず、古いコードを配信していることがある。配信中のファイルに修正箇所が入っているかを確かめてから撮る
- **ホスティングや CDN が配信時にスクリプトを足す構成なら、配信後の URL で、数秒待ってから測る。** 手元のファイルでは正しくても、読み込みの後で書き換えられる
